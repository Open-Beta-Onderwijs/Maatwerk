## Summary

T23 is correct and well tested. The workers check a `Mutex<HashSet>` of failed opdrachten
before they start a job. A skipped job still counts in the progress. Jobs of one opdracht that fail
at the same time are reported once, with their lowest index (`t23_parallel_failures_…`). The error
text keeps the reference's `Fout in opdracht "<label>":` block and puts several under a count line.
`render.rs` only fills in `opdracht: job.opdracht_id`, and maatwerk-core still has no tauri
dependency.

F-14 matches the data-files-v3 rule: below `onder` or `N`/`null` matches, empty or
not-a-number does not (unit table in `opdrachten.test.ts`). A PO has no question cards. Cards
whose question is gone are dropped on read. `setExamOpdrachten` writes only the three coupling
fields into the latest exam on disk, and drops a key when its list is empty.

F-15 has 224 icons. All 50 old icons are still there (tested). There are no ZWJ sequences, and a
range check found nothing newer than Emoji 12.0. An icon that is not in the list shows under
"Huidig".

U10 does what it says. The iframe names one of three files, and the main window builds the path
for the opdracht it opened. The image calls use that opdracht. Unknown types get an error. Both
sides check `evt.source`. The live editor commands check their `path` with `rel()` against the
session root. Every user string in the new modals goes through `escHtml`. The new HTML has no
`style="…"`. Positions are set through the CSSOM.

The main finding is the status pill. It now shows "Opgeslagen · PDF bijgewerkt" whenever the
message is empty. Because of the new rule that typing keeps an error in place, it says
"Opgeslagen" in cases where nothing has been saved yet. Second is a divider bug: a double-click
reset to 50% is never saved. The other findings are small data-safety points that the TS rewrite
carried over, accessibility of the new toolbar menus, and test gaps.

## Majors

### M1. The status pill claims "Opgeslagen · PDF bijgewerkt" when nothing was saved

`ui/src/editor/status.ts:128-131, 197-201, 215-218`; `ui/src/editor-init.js:89, 711-715, 830,
834, 924`

`render()` maps the empty message to the green "Opgeslagen · PDF bijgewerkt" (`message.text ===
''`). The old code showed an empty status there. Three paths now give a false claim:

1. **Fixing a compile error.** While a render error shows, typing no longer sets "Niet
   opgeslagen…" (`editor-init.js:924`, a STATE choice). When the fix compiles,
   `showCompileResult` calls `setStatus('')` (line 714), so the pill turns green and says
   "Opgeslagen". But the save runs only 600 ms after the last key press (`scheduleSave`). If that
   save then conflicts or fails, the pill was wrong. A teacher who fixes an error sees this every
   time.
2. **After any error with details.** `hasRenderError()` is true for every message with
   `details`. That includes "Fout bij opslaan", "Fout bij afbeelding", "Herstellen mislukt" and
   "Fout bij kopiëren". So after a failed save, typing keeps "Fout bij opslaan". The next good
   compile then replaces it with "Opgeslagen · PDF bijgewerkt", while `lastSaveFailed` is still
   true. With a lasting cause (a read-only data folder, a locked file), the pill switches between
   the save error and a green "Opgeslagen" on every pause in typing.
3. **Opening.** `initStatus` renders straight away, before the file is loaded and before the
   opening compile, so the editor starts with "Opgeslagen · PDF bijgewerkt" over an empty preview.
   The first e2e assertion (`editor-shell.spec.ts:35-36`) passes in this state too.

F-05 is the teacher's only save indicator, so a false "Opgeslagen" is a data-safety issue. The
close path (`closeAfterSave`) still saves, but a teacher may stop trusting the pill, or trust it
when they should not.

Fix:

- Track whether the editor is dirty (`saveTimer !== null`, a pending `saving`, or
  `lastSaveFailed`), and show OK only when it is not dirty and the last result is good.
- Keep render errors (compile diagnostics) apart from action errors: for example `setStatus(text,
details, kind)` with `kind: 'render' | 'error'`, and `hasRenderError()` true only for `render`.
- Start with an empty pill, or "Laden…", until the first compile result.
- Add an e2e test: type an error, fix it, and assert that the pill does not say "Opgeslagen" before
  the write (the mock's write log), plus a test with a failing write.

## Minors

### m1. Divider: a double-click reset to 50% is not saved when the saved split differs

`ui/src/editor/divider.ts:28-46, 75-78`; `ui/src/editor-init.js:337-360`

`saved` starts at `clampEditorSplit(initial)`, and `initial` is always `0.5`. The saved position
arrives later through `divider.set(info.split)`, which does not update `saved`. With a saved split
of 0.7, a double click (or a drag or keys that end at exactly 50%) gives `split === saved`, so
`commit()` returns and nothing is saved. The next open goes back to 70%. The e2e test
double-clicks before anything is saved, so it does not catch this.

Fix: let `set()` take an option that also sets `saved` (for example `set(v, { baseline: true })`),
used for the loaded value. Or pass the loaded split as `initial`. Add the reopen-after-reset case
to `editor-shell.spec.ts`.

### m2. "Inhoud bewerken in de editor" writes an unchanged opdracht, and a stale cache blocks the editor

`ui/src/modals/opdracht-edit.ts:143-187`

For an existing opdracht, the button always calls `save()`. This means `upsertOpdracht` with the
cached rev: a write and a new `_meta` stamp ("changed by") each time a teacher only wants to edit
the content. If a colleague changed the opdracht's metadata since it was loaded, the save fails
with a conflict, and the editor does not open (the global handler shows "Sluit het venster…"). The
list's own editor button does not save.

Fix: for an existing opdracht whose snapshot equals `initial`, skip the save and open the editor
straight away. Save only when something changed (a new opdracht still needs its folder first).

### m3. Opdracht save drops fields the modal does not know (carried over from the JS)

`ui/src/modals/opdracht-edit.ts:158-167`; `ui/src/store.js:1107-1114`

`saved` lists only `id, naam, beschrijving, schoolsoort, vakken, jaarlagen, observaties`, and
`upsertOpdracht` writes exactly that. Any other field in `opdracht.json` is lost on every save.
That includes additive fields from a newer app, which the data rules say an older app keeps. The
old `opdrachten.js` did the same, but this step rewrote the modal. `observatie-edit.ts` does it
right (`{ ...obs, … }`).

Fix: `const saved = { ...data, id, naam, … }` (`data` is the `structuredClone` of the cached
record), with `_meta` handled by `saveEntity` as now. Add a unit or e2e check that an unknown
field survives a save.

### m4. Answers still in flight from a closed editor can reach the next editor frame

`ui/src/modals/editor.ts:97-111, 136-146`; `ui/src/editor-init.js:73-79`

`send` posts to `frame.contentWindow` when the answer resolves, not to the window that asked.
Suppose the teacher closes the editor and opens another opdracht while a call is pending (a read,
`maatwerk-save-copy`, an image import). The answer then goes to the new iframe. Its `_seq` also
starts at 1, so the id can match one of the new frame's pending requests. A `read-text-versioned`
answer for opdracht A could then be loaded as opdracht B's text. The hash check makes a silent
overwrite unlikely (the next save conflicts), but the teacher would see the wrong text and a
conflict bar. This was the same in `editor.js`, but U10 is the step that types this channel.

Fix: capture `const target = evt.source as Window` and answer only `if (messageHandler ===
handler)`. Or give each open a nonce (in the URL) that the iframe sends with each request and the
proxy echoes back.

### m5. Toolbar menus use `role="menu"` without menu keyboard behaviour

`ui/editor.html:177-300`; `ui/src/editor-init.js:1205-1240`

The Wiskunde/Symbolen/Opmaak popups are `role="menu"` with `role="menuitem"` children, and the
triggers have `aria-haspopup="menu"`. But:

- opening does not move focus into the menu;
- there is no arrow-key navigation;
- Escape does not close the menu (the e2e test presses Escape and then has to click elsewhere,
  `editor-shell.spec.ts:144-146`);
- the triggers have no `aria-expanded`.

A screen reader announces a menu that does not behave like one. Spec 6 asks for keyboard-operable
controls.

Fix: either implement the menu pattern (focus the first item on open, ArrowUp/Down,
Home/End, Escape returns focus to the trigger, `aria-expanded` on the trigger), or drop the menu
roles and keep plain buttons in a disclosure (`aria-expanded`, Escape closes).

### m6. The status live region announces every compile; re-renders close the popover and drop focus

`ui/src/editor/status.ts:168-204, 221-234`; `ui/editor.html:33`

The pill is `role="status" aria-live="polite"`. Each pause in typing now changes it twice
("Compileren…", then "Opgeslagen · PDF bijgewerkt"), so screen-reader users hear both after every
few keystrokes. `render()` also runs on every `setCompiling` change and always calls
`closePopover()`. It rebuilds `#btn-render-error`, so an open diagnostics popover closes, and a
focused error button loses focus whenever a compile starts or ends.

Fix:

- Put the spinner text in an `aria-hidden` element, or announce only changes of kind
  (error ↔ ok), for example through a separate visually hidden live region.
- In `render()`, keep the popover open and the button in place while the message is the same.

### m7. Coupling saves still replace a colleague's concurrent coupling change (now also for vraag cards)

`ui/src/modals/opdrachten-genereren/index.ts:138-154, 329-345`; `ui/src/store.js:1163-1185`

`setExamOpdrachten` writes `opdrachten`, `opdrachtenCijfer` and `opdrachtenVraag` as whole values
into the latest exam. When a colleague changes this exam while the modal is open, the reload
notice first runs `saveCoupling(state)`. If both teachers changed the coupling, ours replaces
theirs completely. Their new question card or coupling is lost without a message. The same was
true for `opdrachten`/`opdrachtenCijfer` before, but F-14 adds a third list. Low risk (two teachers
editing the same exam's coupling at the same time).

Fix: in the reload path, compare the incoming `ev.after` coupling with `state.savedJson`. If the
colleague changed it too, ask (or merge per card id) instead of saving blindly. At least record this
as a known limit in `quirks.md`.

- U10 (`editor-shell.spec.ts:150-180`) tests only reads. Untested: a write with a bad `file`,

  from `window.parent`.
- `editor/status.ts` and `editor/divider.ts` have no unit tests, although both are pure enough for
  jsdom (`setCompiling` with fake timers, the kinds, `commit` only on a real change). M1 and m1
  would have shown up there.
- The header test (`editor-shell.spec.ts:39-43`) does not assert the intermediate "Niet
  opgeslagen…" state or that the text reached the file.
- `obs-opd.spec.ts` has no case for an observatie whose icon is not in the list ("Huidig").

## Choices made without asking (STATE): assessment

- Step 30: the default vraag card, a fractional limit, 🔢, PO without question cards,
  not-a-number never matches, T23 skipping the failed opdracht's other jobs, the separator text,
  Emoji ≤12.0, "Huidig", pressed category buttons, the Vakken row, "Inhoud bewerken" saving first,
  and dropping hidden observaties. All harmless, except "saves first", which needs the
  unchanged-opdracht exception (m2). Skipping jobs assumes that a failure does not depend on the
  student. A Typst error does not, because student data goes in as inputs. A panic could, in
  theory, but the report would still name the opdracht.
- Step 31: the menu grouping, the 200 ms spinner delay, the 0,5 s key save, Home/End, and the
  light-only editor are fine. Two choices are risky in combination: **"Opgeslagen" and an empty
  message both show "Opgeslagen · PDF bijgewerkt"** together with **"typing keeps a render error
  until the next good compile"**. Together they cause M1.

## Resolution (main session, 2026-11-17)

- **M1 fixed:** `editor/status.ts` keeps three inputs apart: the action message (`setStatus`),
  the compile error of the current text (`setRenderError`) and unsaved edits (`setDirty`).
  "Opgeslagen · PDF bijgewerkt" shows only when nothing is unsaved; a failed save stays until a
  save works; the pill says "Laden…" until the first compile result. e2e `editor-shell.spec`
  "a failed save stays in the pill after a good compile".
- **m1 fixed:** the divider's loaded position counts as saved (`divider.ts` `set`).
- **m2 fixed:** an unchanged opdracht opens the editor without being written.
- **m6 partly fixed:** the pill re-renders only when its state changes, so the popover and focus
  survive compiles that change nothing; the live region stays (role="status" per spec 4.8).
- **Backlog (not fixed in this step):** m3 (unknown fields dropped, as the JS did), m4 (in-flight
  answers after close, as before U10), m5 (menu keyboard behaviour), m7 (coupling saves replace a
  colleague's concurrent coupling, as before), m8 (unit tests for `status.ts`/`divider.ts` need a
  DOM test environment; e2e covers them), the nits.
